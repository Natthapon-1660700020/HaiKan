# HaiKan (ให้กัน)

เว็บส่งต่อสิ่งของฟรีในชุมชนสำหรับวิชา CS319 Internet Programming ผู้ชมเลือกพื้นที่และดูประกาศได้ทันที สมาชิกใช้บัญชีเดียวเพื่อให้ของ ขอรับ และเข้าคิวสำรอง เจ้าของและผู้รับที่ยืนยันสิทธิ์แล้วจึงเห็นจุดนัดละเอียดและช่องทางติดต่อ

## เริ่มใช้งานหลังดาวน์โหลด ZIP จาก GitHub

**1. แตก ZIP แล้วเปิด Terminal ในโฟลเดอร์หลัก** ปกติชื่อ `HaiKan-main` ให้ดูว่าในโฟลเดอร์เดียวกันมี `package-lock.json`, `client` และ `server` โปรเจกต์นี้ทดสอบด้วย Node.js 24 และ npm 11

**2. รัน `npm ci` เป็นคำสั่งแรก** เพื่อติดตั้งแพ็กเกจของทั้ง client และ server ในครั้งเดียว จากนั้นสร้าง Prisma Client

```powershell
npm ci
npm run generate -w server
```

**3. เชื่อมฐานข้อมูลของกลุ่ม** ถ้าใช้ Supabase เดิมที่เตรียมไว้แล้ว ให้นำไฟล์ `server/.env` จากเครื่องเดิมมาวางในโฟลเดอร์ `server` ผ่านช่องทางส่วนตัว แล้วรันคำสั่งนี้จากโฟลเดอร์หลัก

```powershell
npm run check:db -w server
```

**4. เปิดเว็บ** เมื่อทั้ง runtime และ migration แสดงว่าเชื่อมต่อสำเร็จ และฐานเดิมมี migration ครบแล้ว ให้เปิด Terminal สองหน้าต่างในโฟลเดอร์หลัก

| หน้าต่าง | คำสั่ง |
|---|---|
| Terminal 1 | `npm run dev:server` |
| Terminal 2 | `npm run dev:client` |

เปิด **http://localhost:5173** และเปิดทั้งสอง Terminal ค้างไว้ระหว่างใช้งาน ครั้งต่อไปบนเครื่องเดิมเริ่มจากขั้นที่ 4 ได้เลย หาก PowerShell บล็อก `npm.ps1` ให้พิมพ์ `npm.cmd` แทน `npm` เช่น `npm.cmd ci`

### กรณีตั้งค่า Supabase ใหม่

1. เปิด `server/.env` ในเครื่อง ถ้าเพิ่งแตก ZIP ให้คัดลอก `server/.env.example` เป็น `server/.env` ก่อน เมื่อตั้งค่าไว้แล้วให้เก็บไฟล์เดิม
2. ใช้ข้อมูลจากปุ่ม **Connect** ของ Supabase โปรเจกต์เดียวกัน ใส่ `DATABASE_URL` เป็น Shared Transaction Pooler พอร์ต **6543** พร้อม `pgbouncer=true` และใส่ `DIRECT_URL` เป็น Shared Session Pooler พอร์ต **5432** ใช้ชื่อผู้ใช้ของ pooler ที่มี project reference ตามที่ Supabase แสดง หากรหัสผ่านมีอักขระพิเศษให้ URL-encode เฉพาะรหัสผ่าน
3. ใช้ TLS (`sslmode=require`) สำหรับสภาพแวดล้อมทั่วไป บนเครื่องมหาวิทยาลัยที่ต้องใช้ `sslmode=disable` ให้ใส่ค่าตาม URL ที่ได้รับทั้งสองช่องและใช้เฉพาะข้อมูลเดโม คงค่า SSL Enforcement ของโปรเจกต์ไว้ตามเดิม
4. `CLIENT_ORIGIN=http://localhost:5173` ต้องตรงกับ URL ที่เปิดในเบราว์เซอร์ ค่าฐานข้อมูลทั้งหมดอยู่ฝั่ง Express ไฟล์ตัวอย่างไม่มีข้อมูลเชื่อมต่อจริง

โปรเจกต์ล็อก **Prisma 6.19.3** ไว้ใน package-lock จึงกำหนด `url = env("DATABASE_URL")` และ `directUrl = env("DIRECT_URL")` ใน `server/prisma/schema.prisma` คำสั่ง workspace ด้านล่างรันจาก `server/` โดยอัตโนมัติ

```powershell
npm run check:db -w server
npm run migrate -w server
npm run seed -w server
```

`check:db` ทดสอบ SELECT 1 แยกสองช่องทางและรายงานผลโดยปิดบัง URL พอร์ต 6543 ใช้กับเว็บและ seed พอร์ต 5432 ใช้กับ migration ถ้ารายงานว่ารอการตั้งค่า ให้ตรวจ placeholder ใน .env ถ้าติดต่อปลายทางไม่ได้ให้ตรวจ host ภูมิภาค เครือข่าย และสถานะโปรเจกต์ หากยืนยันตัวตนไม่ได้ให้ตรวจชื่อผู้ใช้ pooler และรหัสผ่าน

`migrate` ใช้ `prisma migrate deploy` กับ migration ที่เก็บในโปรเจกต์ จากนั้น seed จะเพิ่มประกาศตัวอย่าง 48 รายการจาก 4 หมวดและ 7 พื้นที่ ใช้รหัสประกาศเดิมทุกครั้งและเว้นข้อมูลที่สร้างไว้แล้ว จึงรันซ้ำหลังเดโมได้ ใช้โปรเจกต์ Supabase สำหรับข้อมูลสมมติของกลุ่ม

### รัน Frontend และ Backend

เปิดสองเทอร์มินัลที่รากโปรเจกต์

| เทอร์มินัล | คำสั่ง | ที่อยู่ |
|---|---|---|
| Backend | `npm run dev:server` | `http://localhost:4001/api/items` เมื่อตั้ง `PORT=4001` |
| Frontend | `npm run dev:client` | `http://localhost:5173` |

เปิดเว็บที่ **http://localhost:5173** Vite อ่านค่า `PORT` จาก `server/.env` ตอนเริ่มทำงานและส่งต่อเส้นทาง `/api` ไป Express เมื่อเปลี่ยนพอร์ตให้เริ่มทั้งสองเทอร์มินัลใหม่ คุกกี้ session ใช้ได้ผ่าน origin เดียวกัน

```powershell
npm run typecheck
npm run build
```

คำสั่งสองบรรทัดนี้ตรวจทั้ง client และ server ตามลำดับ ไฟล์ build อยู่ใน `client/dist` และ `server/dist` หากต้องการรัน Express จากไฟล์ build ใช้ `npm start -w server`

## Live Demo Phase 1

1. เปิดหน้าสำรวจในหน้าต่างปกติ ดูการ์ดจริง เลือก **กรุงเทพมหานคร → จตุจักร** แล้วเปิดรายละเอียด สังเกต `/items/:id` พื้นที่คร่าว ๆ และช่องทางติดต่อที่จำกัดสิทธิ์
2. เข้าบัญชีผู้ให้ กด **ลงประกาศส่งต่อ** ตั้งชื่อเฉพาะสำหรับรอบนี้ เลือกจังหวัดกับอำเภอ กรอกรายละเอียด จุดนัด และช่องทางติดต่อสมมติ เลือก **นัดรับภายหลัง** ยืนยันสิทธิ์แล้วบันทึก เปิด **ประกาศของฉัน** หาใบที่สร้าง และเก็บรหัสจาก URL
3. เปิดหน้าต่าง InPrivate อีกหน้าต่าง ค้นชื่อและกรองพื้นที่ของประกาศใหม่ ดู response ของ `GET /api/items/:id` ผ่าน DevTools → Network ค่า `pickup` ของผู้ชมคือ `null` และไม่มีข้อความจุดนัดหรือช่องทางติดต่อ
4. ในหน้าต่างที่สองกดเข้าสู่ระบบจากรายละเอียดด้วยบัญชีผู้รับ ยืนยันว่ารับตามเงื่อนไขได้แล้วกด **ขอรับสิ่งของ** ป้ายเปลี่ยนเป็น **จองแล้ว** ในหน้าเดิม และจุดนัดละเอียดปรากฏ
5. เปิด **คำขอของฉัน** ดูสถานะรอนัดรับและเวลาที่ต้องตกลง เปิด Supabase Dashboard → Table Editor → `public.Item` กรอง `id` ตาม URL แล้วตรวจ `state = RESERVED` ใน `public.Claim` กรอง `itemId` เดียวกัน ตรวจ `state = CONFIRMED` และ `userId` ของผู้รับ
6. เปิดไฟล์ตามแผนที่ด้านล่าง สาธิตการเลือกพื้นที่อีกครั้งแล้วชี้พารามิเตอร์ที่เปลี่ยนใน Network ระหว่างเดโมให้แสดงเฉพาะตารางและคอลัมน์ที่เกี่ยวข้องกับข้อมูลสมมติ

เนื้อหาพร้อมจัดสไลด์และลำดับเปิดหน้าจออยู่ใน [สไลด์ Phase 1](docs/phase-1-slides.md)

## แผนที่โค้ดสำหรับ Quiz

| เรื่อง | UI → Query Hook → Express → Prisma |
|---|---|
| กรองจังหวัดและอำเภอ | [Catalog.tsx](client/src/Catalog.tsx) เขียนตัวกรองลง URL และล้างอำเภอเมื่อเปลี่ยนจังหวัด → [useAreas / useItems](client/src/api.ts) สร้าง query key จากตัวกรอง → [GET /areas และ /items](server/src/items.ts) ตรวจ query และประกอบ where → `db.item.findMany` เลือกเฉพาะ publicFields |
| ขอรับ | [Detail.tsx](client/src/Detail.tsx) รับคำยืนยัน → [useAction](client/src/api.ts) ส่ง POST และ invalidate หลังสำเร็จ → [POST /items/:id/claims](server/src/items.ts) ตรวจสมาชิกกับเงื่อนไข → [reserve และ withItem](server/src/queue.ts) ล็อกแถวประกาศ สร้าง Claim และเปลี่ยน Item ใน transaction เดียว |
| สิทธิ์ดูจุดนัด | [หน้ารายละเอียด](client/src/Detail.tsx) และ [คำขอของฉัน](client/src/Lists.tsx) → `useDetail / useClaims` → [items.ts](server/src/items.ts) อ่านเจ้าของและผู้ขอ → [pickupDetails](server/src/presentation.ts) ประกอบข้อมูลส่วนตัวหลังตรวจสิทธิ์ |
| จัดการและเลื่อนคิว | [Management.tsx](client/src/Management.tsx) → `useAction` → [management.ts](server/src/management.ts) ตรวจเจ้าของหรือผู้ขอ → [advanceQueue](server/src/queue.ts) เลือก WAITING ที่มี id ต่ำสุด |
| บันทึกและดูแล | [saved.ts](client/src/saved.ts) เก็บเฉพาะ id ใน LocalStorage → [Lists.tsx](client/src/Lists.tsx) ขอรายละเอียดล่าสุดจาก `GET /saved/:id` → [moderation.ts](server/src/moderation.ts) จัดการรายงานและเหตุผลในการตัดสิน |

**ลองแก้ในคาบ** หากเพิ่มตัวกรองสภาพสิ่งของ ให้เริ่มที่ `Filters` ใน `client/src/model.ts` เพิ่มตัวเลือกใน Catalog และส่งค่าผ่าน useItems จากนั้นเพิ่มตัวตรวจ query และฟิลด์ใน Prisma where ของ `GET /items` หากเปลี่ยนเวลายืนยันคิวสำรอง ให้แก้ `offerDeadline` ใน queue.ts และปรับค่าที่คาดหวังในชุดทดสอบคิว

## กติกา Final ที่เดโมได้

ประกาศที่ปิดหรือส่งต่อแล้วไม่มีวันหมดอายุ เจ้าของกด “นำออกจากหน้าสาธารณะ” ในหน้ารายละเอียดได้ ผู้ที่เคยขอรับยังเปิดประวัติจากหน้าคำขอของฉันได้

- **รูปประกาศ** เลือกไฟล์ JPG, PNG หรือ WebP ได้หนึ่งรูป ขนาดไม่เกิน 5 MB ฟอร์มจะแสดงตัวอย่างก่อนบันทึก หากสร้างประกาศโดยไม่เลือกรูป ระบบใช้ภาพตามหมวด หากแก้ไขข้อความเพียงอย่างเดียว ระบบเก็บรูปเดิมไว้
- **การเก็บรูป** [ItemForm.tsx](client/src/ItemForm.tsx) ส่งไฟล์พร้อมข้อมูลประกาศผ่าน multipart ไปยัง Express [photos.ts](server/src/photos.ts) ตรวจชนิดและขนาด ถอดรหัสภาพ และย่อด้านยาวให้ไม่เกิน 1,440 พิกเซลก่อนเก็บเป็น WebP ในตาราง `ItemPhoto` ของ PostgreSQL การบันทึกรูปและประกาศเป็นรายการเดียวกัน เมื่อเปิดการ์ด เบราว์เซอร์โหลดรูปแยกจาก `GET /api/photos/:id`
- **การประกาศ** ฟอร์มเดียวใช้กับของชิ้นเดียวและของเป็นชุด ทั้งชุดใช้คำขอเดียว ไม่มีค่ารับของและไม่มีการชำระเงิน
- **การจองพร้อมกัน** Express ล็อกแถว Item ด้วย `SELECT ... FOR UPDATE` ก่อนอ่านสถานะ ภายใน transaction เดียวกันจะให้คนแรกเป็น CONFIRMED และคนถัดไปเป็น WAITING ดัชนีบางส่วนใน [migration](server/prisma/migrations/202611210002_invariants/migration.sql) บังคับทั้งผู้ถือสิทธิ์คนเดียวต่อประกาศและคำขอที่กำลังดำเนินอยู่รายการเดียวต่อผู้ใช้ต่อประกาศ
- **คิวและเวลา** เมื่อสละสิทธิ์หรือผิดนัด ระบบเสนอให้คิวถัดไปตาม Claim.id โดยให้เวลาไม่เกิน 2 ชั่วโมงและไม่เกินเวลาสิ้นสุดนัด ถ้าช่วงนัดหมดจะพักคิวและเรียงลำดับเดิมเมื่อมีช่วงใหม่ แบบนัดภายหลังมีเวลา 48 ชั่วโมงนับจากยืนยันสิทธิ์
- **การตกลงนัด** เจ้าของเสนอช่วงใหม่พร้อมเหตุผลจากหน้ารายละเอียด ผู้จองเดิมยืนยันหรือสละสิทธิ์จาก “คำขอของฉัน” เมื่อเลยช่วงนัดที่ยืนยันแล้ว เจ้าของจึงยืนยันว่าผิดนัดได้ หลังส่งมอบจริงเจ้าของกด “ส่งต่อแล้ว” ระบบจบคำขอและคิวที่เกี่ยวข้อง
- **การหมดเวลาอัตโนมัติ** Express ตรวจคำขอที่ถึงกำหนดทุก 15 วินาทีและก่อนประมวลผลข้อมูลประกาศ หน้าเว็บที่เปิดอยู่ขอข้อมูลใหม่ทุก 15 วินาทีด้วย TanStack Query เวลาในฐานข้อมูลและฝั่งเซิร์ฟเวอร์เป็นตัวตัดสินสิทธิ์
- **ประวัติ** เจ้าของลบได้เฉพาะประกาศที่ยังไม่เคยมีคำขอ ถ้าเคยมีคำขอให้ปิดพร้อมเหตุผล รายการบันทึกเปิดดูได้ทั้งของที่หมดช่วงหรือส่งต่อแล้ว รายการที่ถูกซ่อนหรือลบจะแสดง “ประกาศนี้เปิดดูไม่ได้” และนำออกได้
- **ผู้ดูแล** สมาชิกรายงานประกาศพร้อมเหตุผลได้หนึ่งครั้งต่อประกาศ ผู้ดูแลเห็นตัวตนผู้รายงานและบันทึกผลซ่อน เปิดคืน หรือปิดใน Decision ระหว่างซ่อนจะระงับการจองและพักเวลา เมื่อเปิดคืนหลังนัดเดิมสิ้นสุด ผู้ให้ต้องเสนอช่วงใหม่เพื่อให้ผู้จองเดิมยืนยัน

**สถานะ Supabase วันที่ 22 พ.ย. 2569** ตรวจ SELECT 1 ผ่านทั้งพอร์ต 6543 และ 5432 จากเครื่องพัฒนา หน้าเว็บอ่านประกาศจริง 48 รายการและพื้นที่ 7 แห่งผ่าน Express ได้ ตรวจด้วย Edge แล้วหน้าสำรวจแสดงการ์ด 12 ใบในหน้าแรก ส่วนการจองด้วยสองบัญชีบน Supabase และการเข้าถึงจากเครื่องมหาวิทยาลัยยังรอทดสอบ ทดสอบการอัปโหลดผ่าน Edge กับ Supabase แล้ว ทั้งสร้างประกาศ เปลี่ยนรูป แก้ข้อความโดยคงรูปเดิม เลือกใช้ภาพตามหมวด และลบรูปพร้อมประกาศ ภาพหน้าสร้างและแก้ไขใน [โฟลเดอร์ screenshots](docs/screenshots) มาจากการทดสอบนี้ ส่วนภาพหน้าอื่นมาจากฐานทดสอบ PostgreSQL บนเครื่อง

[ชุดทดสอบคิว](server/tests/acceptance.ts) ใช้ Express ที่พอร์ต 4000 และ Prisma กับฐานทดสอบแยกบน `127.0.0.1:55439` เท่านั้น เพื่อจำลองเส้นตายให้ทดสอบกรณี 2 และ 48 ชั่วโมงได้ทันที คำสั่ง `npm run test:queue -w server` ต้องรันเมื่อ API และตัวทดสอบชี้ฐานทดสอบเดียวกันที่ migrate/seed แล้ว ชุดทดสอบสร้างบัญชีและประกาศเฉพาะรอบและเก็บกวาดเมื่อจบ
